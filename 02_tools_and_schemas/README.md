# Модуль 02. Схемы данных и вызов инструментов

> Здесь решаются две главные проблемы нейросети. Первая: она отвечает свободным текстом, а программе нужны предсказуемые данные. Вторая: она умеет только писать текст, а программе нужны реальные действия (посчитать, найти, записать).

| Часть | Идея | Файлы |
| :--- | :--- | :--- |
| А. Структурированный вывод | Модель заполняет «анкету» (схему) вместо свободного рассказа | `step2_structured_output.py`, `structured_output_exericise.py` |
| Б. Вызов инструментов | Модель выбирает функцию, а выполняет её ваш Python | `step3_tool_calling.py` |

В названии файла `structured_output_exericise.py` опечатка («exericise»). Она оставлена как есть, чтобы не менять историю репозитория.

# ЧАСТЬ А. Структурированный вывод

## А.1. Объяснение для новичка

Попросите человека «расскажи про Redis», и он расскажет как получится: коротко или на страницу, с примером или без. Программе такой рассказ неудобен: непонятно, где название, где плюсы, где минусы.

Теперь дайте человеку анкету с графами «Название», «Описание», «Плюсы (2–3 пункта)», «Минусы (1–2 пункта)», «Когда применять». Ответ всегда будет в одной и той же форме, и программа без труда достанет любую графу.

Класс Pydantic — это и есть анкета, а нейросеть — тот, кто её заполняет.

## А.2. Объяснение для профи

- Метод `with_structured_output(Схема)` принимает класс Pydantic, превращает его в описание формата и передаёт провайдеру вместе с запросом. Конкретный механизм (вызов функции или строгий режим JSON) зависит от версии библиотеки и от модели.
- Ответ модели разбирается и проверяется по схеме. На выходе вы получаете готовый объект вашего класса, а не строку. Поэтому `StrOutputParser` здесь не нужен.
- При несоответствии типов или пропуске обязательного поля возникает исключение разбора или проверки (например, `ValidationError`). Для бесплатных моделей через OpenRouter это случается чаще: не все они хорошо держат формат.
- Описания полей (`Field(description=...)`) и строка документации класса — часть запроса. Чем точнее описание, тем лучше заполнение.
- Температуру для таких задач держат низкой (в файле 0.2): нужны данные, а не фантазия.

## А.3. Термины

| Термин | Простыми словами | Техническая суть |
| :--- | :--- | :--- |
| Pydantic | Библиотека-контролёр данных | Проверяет типы и обязательность полей |
| `BaseModel` | Бланк анкеты | Базовый класс для описания схемы |
| `Field(description=...)` | Подсказка к графе | Описание поля, которое читает модель |
| Аннотация типа (`str`, `List[str]`) | Что именно должно быть в графе | Тип значения; по нему идёт проверка |
| Строка документации класса | Заголовок анкеты | Описание всей схемы, также уходит модели |
| `with_structured_output` | «Заполни именно эту анкету» | Привязывает схему к модели |
| Валидация | Проверка заполнения | Pydantic сверяет ответ со схемой |
| `ValidationError` | «Анкета заполнена неверно» | Исключение при несоответствии |
| Низкая температура | Режим «без фантазий» | Меньше случайности в ответах |

## А.4. Схема `TechnologyAnalysis` (файл `step2_structured_output.py`)

| Поле | Тип | Что должна вписать модель |
| :--- | :--- | :--- |
| `name` | `str` | Название технологии или паттерна |
| `summary` | `str` | Краткое описание назначения (1–2 предложения) |
| `pros` | `List[str]` | Список из 2–3 преимуществ |
| `cons` | `List[str]` | Список из 1–2 недостатков |
| `recommended_use_case` | `str` | Идеальный сценарий применения |

## А.5. Кто что выполняет

| Шаг | Действие | Кто выполняет |
| :--- | :--- | :--- |
| 1 | Описывает анкету (схему) | Вы |
| 2 | Привязывает схему к модели | `with_structured_output(...)` |
| 3 | Подставляет технологию в шаблон | `ChatPromptTemplate` |
| 4 | Заполняет анкету по тексту запроса | Нейросеть |
| 5 | Разбирает ответ и проверяет его | LangChain и Pydantic |
| 6 | Выдаёт готовый объект | `chain.invoke(...)` |

Цепочка устроена так:

```text
 {"technology": "Redis"} ──► шаблон ──► модель + схема ──► объект TechnologyAnalysis
```

## А.6. Разбор кода `step2_structured_output.py`

| Фрагмент | Что происходит |
| :--- | :--- |
| `class TechnologyAnalysis(BaseModel)` | Описание анкеты с пятью графами |
| `llm.with_structured_output(TechnologyAnalysis)` | Модель теперь обязана отвечать по этой схеме |
| `chain = prompt \| structured_llm` | Цепочка из шаблона и «модели с анкетой» |
| `chain.invoke({"technology": "Redis"})` | Запуск; на выходе объект класса `TechnologyAnalysis` |
| `result.name`, `result.pros` и т. д. | Обычные атрибуты Python-объекта, а не поиск по тексту |

Пример результата (формат точный, текст сгенерирует модель и он будет другим):

```text
--- РЕЗУЛЬТАТ: ВАЛИДИРОВАННЫЙ ОБЪЕКТ PYDANTIC ---
Тип объекта: <class '__main__.TechnologyAnalysis'>
Технология : Redis
Описание   : Хранилище данных в оперативной памяти для быстрого доступа.
Плюсы      : высокая скорость, богатые структуры данных
Минусы     : ограничен объёмом памяти
Сценарий   : кэширование, очереди, счётчики
-------------------------------------------------
```

## А.7. Упражнение `structured_output_exericise.py` и ловушка со временем

В упражнении своя схема `AnswerOutputSchema` с тремя полями: `name`, `answer` и `datetime` (тип «дата и время»).

**Ловушка.** У нейросети нет часов. Поле «время ответа» она заполнит выдуманным значением, которое выглядит правдоподобно, но не имеет отношения к настоящему времени. Это хороший урок: схема гарантирует форму, но не правдивость данных.

Правильно брать время из кода, а не от модели:

```python
from datetime import datetime

result = chain.invoke({"text": input_text})
real_time = datetime.now()   # настоящее время берём у компьютера
```

Замечания по файлу:

- Поле названо `datetime` и в то же время имеет тип `datetime`. Пока у поля нет значения по умолчанию, это работает. Если раскомментировать `= Field(...)`, имя поля затмит класс, и Pydantic, скорее всего, выдаст ошибку. Надёжнее назвать поле иначе, например `answered_at`.
- Импорты `RunnableLambda` и `Runnable` в файле не используются, их можно убрать.

## А.8. Частые ошибки

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Ошибка разбора или проверки | Модель не уложилась в схему | Упростить схему, уточнить описания полей, снизить температуру, сменить модель |
| Поля пустые или странные | Мало подсказок в описаниях | Писать конкретные `Field(description=...)` |
| Время ответа «неправильное» | Модель его выдумала | Брать время из кода (раздел А.7) |

# ЧАСТЬ Б. Вызов инструментов (Tool Calling)

## Б.1. Главный принцип

**Модель сама ничего не выполняет.** Она лишь решает, какая функция нужна, и называет аргументы. Запускает функцию ваш Python.

## Б.2. Объяснение для новичка

Представьте диспетчера в компании. Клиент спрашивает: «Сколько стоит аренда 6 серверов на 150 часов?» Диспетчер сам не считает. Он говорит: «Возьмите калькулятор «стоимость серверов» и посчитайте: 6 машин, 150 часов». Вы нажимаете кнопки, получаете число 45.0 и возвращаете его диспетчеру. Тот красиво отвечает клиенту.

| Роль в истории | Кто это в коде |
| :--- | :--- |
| Клиент | Пользователь с вопросом |
| Диспетчер | Нейросеть |
| Калькулятор | Функция `calculate_server_cost` |
| Тот, кто нажимает кнопки | Ваш скрипт |

## Б.3. Объяснение для профи

- Декоратор `@tool` превращает функцию в инструмент: из имени, аннотаций типов и строки документации строится описание (название, назначение, аргументы). Весь текст строки документации уходит модели, поэтому писать его нужно как инструкцию.
- `bind_tools(tools)` возвращает модель, которой вместе с каждым запросом передаются описания инструментов.
- Решение модели приходит в поле `tool_calls` объекта `AIMessage`: имя, словарь аргументов и идентификатор вызова. Содержимое `content` при этом обычно пустое.
- Результат инструмента нужно вернуть как `ToolMessage` с тем же `tool_call_id`, предварительно добавив в историю сам `AIMessage` с вызовом. Без этого провайдер отклонит запрос из-за нарушенной последовательности сообщений.
- Список `tool_calls` может содержать несколько вызовов сразу, поэтому в коде стоит цикл.
- В примере один круг «вопрос, вызов, результат, ответ». Настоящий агент повторяет круг, пока модель просит новые вызовы. Именно эту рутину автоматизирует LangGraph (следующие модули).

## Б.4. Термины

| Термин | Простыми словами | Техническая суть |
| :--- | :--- | :--- |
| Инструмент | Функция, которую можно «заказать» у программы | Python-функция с описанием для модели |
| `@tool` | Ярлык «это инструмент» | Декоратор из `langchain_core.tools` |
| Строка документации | Инструкция по применению | Текст внутри тройных кавычек; читает модель |
| Аннотации типов | Указание, что за значение нужно | `int`, `float`: по ним строится схема аргументов |
| `bind_tools` | «Вот ваши инструменты» | Привязка списка инструментов к модели |
| `tool_calls` | Заказ модели на инструмент | Список вызовов в `AIMessage`: `name`, `args`, `id` |
| `tool_call_id` | Номер заказа | Уникальный идентификатор для связи заказа и результата |
| `ToolMessage` | Выполненный заказ | Сообщение с результатом инструмента |
| `tools_by_name` | Справочник «название, функция» | Словарь для поиска функции по имени из `tool_calls` |
| Температура 0 | Режим «минимум случайности» | Рекомендуется для вызова функций; полной гарантии одинаковых ответов не даёт |

## Б.5. Кто что выполняет

| Шаг | Действие | Кто выполняет |
| :--- | :--- | :--- |
| 1 | Задаёт вопрос | Пользователь |
| 2 | Выбирает инструмент и называет аргументы | Нейросеть |
| 3 | Находит функцию по имени и запускает её | Ваш скрипт |
| 4 | Упаковывает результат в `ToolMessage` | Ваш скрипт |
| 5 | Формулирует итоговый ответ по результату | Нейросеть |

## Б.6. Схема

```text
 Пользователь           Нейросеть                 Ваш скрипт
      │                     │                          │
      │ 1. «Сколько стоит   │                          │
      │  6 серверов, 150 ч?»│                          │
      ├────────────────────►│                          │
      │                     │ 2. решает: нужна         │
      │                     │  calculate_server_cost,  │
      │                     │  аргументы {6, 150}      │
      │                     ├─────────────────────────►│
      │                     │                          │ 3. считает 6 × 150 × 0.05 = 45.0
      │                     │                          │ 4. упаковывает в ToolMessage
      │                     │◄─────────────────────────┤    с тем же tool_call_id
      │                     │ 5. формулирует ответ     │
      │◄────────────────────┤                          │
```

## Б.7. Что лежит в списке `messages` на каждом шаге

| Момент | Содержимое списка `messages` |
| :--- | :--- |
| Старт | Сообщение человека с вопросом |
| После 1-го вызова модели | + `AIMessage` (текст пустой, поле `tool_calls` заполнено) |
| После запуска функции | + `ToolMessage` (содержимое «45.0», тот же `tool_call_id`) |
| После 2-го вызова модели | Итоговый ответ лежит в переменной `final_response` (в список скрипт его не добавляет, а только печатает) |

## Б.8. Разбор кода `step3_tool_calling.py`

```python
@tool
def calculate_server_cost(instances: int, hours: int, price_per_hour: float = 0.05) -> float:
    """Рассчитывает общую стоимость аренды серверов в облаке. ..."""
    return round(instances * hours * price_per_hour, 2)
```

| Фрагмент | Что происходит |
| :--- | :--- |
| `@tool` и строка документации | Функция становится инструментом, модель узнаёт, зачем он и что значат аргументы |
| `price_per_hour: float = 0.05` | Необязательный аргумент со значением по умолчанию. Вопрос «при стандартном тарифе» позволяет модели его не указывать |
| `tools_by_name = {t.name: t for t in tools}` | Справочник для поиска функции по имени |
| `llm.bind_tools(tools)` | Модель получает описание инструментов |
| `ai_response = llm_with_tools.invoke(messages)` | Первый вызов: модель решает, что делать |
| `messages.append(ai_response)` | Решение модели обязательно сохраняется в историю |
| `for tool_call in ai_response.tool_calls` | Перебор заказов модели (их может быть несколько) |
| `tools_by_name[tool_name].invoke(tool_args)` | Фактический запуск функции с аргументами от модели |
| `ToolMessage(content=str(tool_output), tool_call_id=tool_id)` | Результат с номером заказа |
| `llm_with_tools.invoke(messages)` | Второй вызов: модель видит результат и пишет ответ |
| Ветка `else` | Если модель обошлась без инструмента, печатается её прямой ответ |

## Б.9. Пример

Вопрос: «Сколько будет стоить аренда 6 серверов на 150 часов при стандартном тарифе?»

Первый вызов, сырой ответ модели (идентификатор у вас будет другим):

```text
Tool calls: [{'name': 'calculate_server_cost', 'args': {'instances': 6, 'hours': 150}, 'id': '...', 'type': 'tool_call'}]
```

Выполнение: 6 × 150 × 0.05 = **45.0**.

Второй вызов: модель получает число 45.0 и пишет связный ответ вида «Аренда 6 серверов на 150 часов обойдётся в 45 долларов» (формулировка зависит от модели).

Для самостоятельной проверки измените вопрос: «10 серверов на 24 часа по цене 0.1 за час». Ожидаемый расчёт: 10 × 24 × 0.1 = 24.0.

## Б.10. Ограничения примера (что улучшить)

| Ограничение | Чем грозит | Как исправить |
| :--- | :--- | :--- |
| Нет проверки имени инструмента | Если модель выдумает имя, будет ошибка `KeyError` | Проверять `tool_name in tools_by_name` |
| Нет обработки ошибок функции | Исключение внутри функции остановит скрипт | Обернуть вызов в `try/except` и вернуть текст ошибки в `ToolMessage` |
| Один круг «вызов, ответ» | Если модели нужен второй инструмент, цикла нет | Повторять, пока есть `tool_calls`; это основа агента |

## Б.11. Частые ошибки

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `tool_calls` пуст, модель отвечает текстом | Модель не поддерживает инструменты или не поняла задачу | Уточнить docstring и вопрос, выбрать другую модель |
| Провайдер возвращает ошибку 400 на втором вызове | В историю не добавлен `AIMessage` с вызовом или неверен `tool_call_id` | Добавлять `ai_response` перед `ToolMessage`, брать `id` из вызова |
| `KeyError` с названием инструмента | Модель назвала функцию, которой нет в справочнике | Проверка имени (см. Б.10) |

# ЧАСТЬ В. Сравнение двух механизмов

| Критерий | Структурированный вывод | Вызов инструментов |
| :--- | :--- | :--- |
| Цель | Получить данные в нужной форме | Выполнить действие или получить внешние данные |
| Кто выполняет работу | Модель заполняет анкету | Ваш Python исполняет функцию |
| Число обращений к модели | Одно | Два (до и после инструмента) |
| На выходе | Объект Pydantic | Текстовый ответ, основанный на результате функции |
| Типичная задача | Разобрать письмо в поля, оценить технологию | Посчитать, найти в базе, запросить погоду |

## Проверь себя

<details>
<summary>1. Почему во второй вызов модели нужно передавать и исходный вопрос, и вызов инструмента, и его результат?</summary>

У модели нет памяти между вызовами. Вся история должна быть в списке сообщений, иначе она не поймёт, откуда взялось число.
</details>

<details>
<summary>2. Кто фактически считает 6 × 150 × 0.05?</summary>

Python-функция `calculate_server_cost` в вашем скрипте. Модель только выбирает функцию и аргументы.
</details>

<details>
<summary>3. Почему поле «время ответа» от модели нельзя считать настоящим временем?</summary>

У модели нет часов, она генерирует правдоподобное значение. Настоящее время берут из кода: `datetime.now()`.
</details>

<details>
<summary>4. Зачем нужен `tool_call_id`?</summary>

Он связывает заказ модели с результатом, особенно когда заказов несколько.
</details>

## Что запомнить

- Схема Pydantic даёт предсказуемую **форму** ответа, но не гарантирует правдивость содержимого.
- Модель выбирает инструмент, а выполняет его ваш код.
- Историю сообщений нужно вести самому: вопрос, вызов, результат.
- Один круг из примера — основа агента, а LangGraph автоматизирует повторение этого круга.
